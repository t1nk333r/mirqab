# Plan 020: Packaging and release

## Status

- **Priority**: P2
- **Effort**: S
- **Risk**: LOW. The one sharp edge is the root helper's unit: the
  package must ship it and must not enable it.
- **Depends on**: 001 to 005 (a first package is possible after M2; it
  is updated as tabs land)
- **Category**: packaging
- **Planned at**: 2026-11-13, from the owner: "packaging for Arch"
- **State**: PLANNED

## Problem

Install with one command on Arch and its derivatives, update through
pacman, remove cleanly. The source is public at
`github.com/t1nk333r/mirqab` (owner, 2026-11-13); publishing a package
to the AUR is still the owner's step.

## Not possible on Linux

Not applicable. Out of scope by choice until the owner asks: Debian and
Fedora packages, Flatpak (the sandbox hides `/proc`, `/sys` and the
system bus this app is made of), Nix, an AppImage, a self-updater.

## Design

### What the package installs

| Path | What |
|------|------|
| `/usr/bin/mirqab` | Daemon, CLI, MCP server |
| `/usr/bin/mirqab-fand` | The root helper binary |
| `/usr/bin/mirqab-ui` | The GTK4 interface (started by `mirqab-ui.service`; not meant to be run by hand) |
| `/usr/share/mirqab/{config.schema.json,report.schema.json,cities.json,landmask.json}` | Data |
| `/usr/lib/systemd/user/{mirqab.socket,mirqab.service,mirqab-ui.service}` | User units |
| `/usr/lib/systemd/system/mirqab-fand.service` | The helper's unit, **not enabled** |
| `/usr/lib/mirqab/{helper-enable,helper-disable}` | The two fixed scripts `pkexec` runs |
| `/usr/share/applications/mirqab.desktop` | Launcher entry (`Exec=mirqab open --window`) |
| `/usr/share/icons/hicolor/scalable/apps/mirqab.svg` | Icon (drawn for this project) |
| `/usr/share/licenses/mirqab/{LICENSE,NOTICE.md}` | Licence and attributions |
| `/usr/share/doc/mirqab/` | README, `docs/helper.md`, bar and keybinding examples |
| Shell completions | bash, zsh, fish, generated by `mirqab completions <shell>` at build time |

Nothing under `/etc`. No `.install` scriptlet enables anything; the
post-install message is three lines: how to start
(`systemctl --user enable --now mirqab.socket`), how to open
(`mirqab open`), and that fan control is off until
`mirqab helper enable`.

`pre_remove` in the `.install` file: if `mirqab-fand.service` is active,
stop it (its stop path returns fans to automatic). It does not touch
`/etc/mirqab` (pacman did not create it); `mirqab helper disable` is the
documented clean-up, and the uninstall section of the README says so.

### Dependencies

`depends`: `gtk4>=4.16`, `libadwaita>=1.6`, `gtk4-layer-shell`, `sqlite`,
`curl`, `ttf-nerd-fonts-symbols`, `polkit`, `tzdata`. (`gtk4`
already depends on `adwaita-icon-theme` and `librsvg` **[machine]**.)
`optdepends`, each with its reason: `pipewire-pulse` with `libpulse` and
`wireplumber` (the Volume tab),
`bluez`, `udisks2`, `upower`, `networkmanager`, `iw`, `bolt`, `docker`,
`avahi`, `geoclue`, `lm_sensors`, `fwupd`, `qrencode`.
`makedepends`: `cargo`, `pkgconf`, `git` (for `-git`). `libpulse` is also
a `makedepends`, because the Volume page links it; the page loads the
library only if present **[unverified]**, see below.

The lists are generated from one table in `dist/deps.toml`, which
`mirqab status` also reads to say which package provides a missing
capability, so the two cannot drift; a test checks the PKGBUILD against
it.

### Two PKGBUILDs

- `dist/PKGBUILD`: builds a tagged release from the tarball, with
  checksums.
- `dist/PKGBUILD-git`: `mirqab-git`, `pkgver()` from `git describe`,
  `provides=(mirqab)`, `conflicts=(mirqab)`.

Both build with `--frozen`, never fetch in `build()`, and run only the
Rust tests that need no display in `check()` (`cargo test --frozen
--workspace --exclude mirqab-ui`; the widget and shell suites need
Broadway and are CI's job).

### Versioning and release

- Semantic versions; `0.x` until the owner calls it 1.0. The protocol
  version in the `hello` frame is separate and bumps only on a breaking
  change.
- `CHANGELOG.md`, one section per version, written from merged plan
  titles.
- `tools/release.sh <version> [--dry-run]`: checks a clean tree on
  `main`, the gates, that `Cargo.toml`, the PKGBUILD and the changelog
  agree, then creates the tag locally. It **does not push**; pushing a
  tag is the owner's step. Dry-run prints the steps.
- CI on a tag: `.github/workflows/release.yml`, the second and last
  workflow file (plan 001 adds `ci.yml`). Job `package`, which also runs
  on pull requests that touch `dist/`; it is not a required check. It
  builds in an `archlinux:latest` container, `makepkg`,
  `namcap` on the PKGBUILD and the built package, the full test suite,
  `tools/bench-idle.sh`, then attach the source tarball and its
  checksum to the release. No binary packages are published unless the
  owner asks.
- Reproducibility: `SOURCE_DATE_EPOCH` honoured; `Cargo.lock` committed;
  `cargo vendor` is not used.

### AUR

Owner steps, listed in `docs/release.md`, not automated: create the AUR
repositories `mirqab` and `mirqab-git`, copy the PKGBUILD and a generated
`.SRCINFO`, push with the owner's AUR key. No key or token is stored in
this repository or its CI.

### Desktop integration examples (docs only, nothing installed into the
user's config)

- Hyprland: a bind for `mirqab toggle`, and a window rule for the
  popover.
- Waybar: `contrib/waybar/` module examples for `mirqab bar <item>
  --watch`.
- haseen: `contrib/haseen/mirqab.bar/`, installed by the owner with
  `haseen plugin install`; this package never writes into another
  project's directories.

## Rejected

- **Enabling the user socket from the package.** Packages do not enable
  user units for people; one printed line does.
- **Enabling the helper from the package.** The owner's rule: opt-in.
- **Flatpak.** See above.
- **Binary releases on GitHub.** An unsigned binary of a tool with a
  root helper is a poor habit; build from source through the PKGBUILD.
- **A `-bin` AUR package.** Same reason.
- **cargo-dist, cargo-release.** More tooling than one script.
- **A self-updater.** pacman.

## Tests and fixtures

| Test | Checks |
|------|--------|
| `tests/test-packaging.sh` | `bash -n` on both PKGBUILDs; `depends` and `optdepends` equal `dist/deps.toml`; the file list in `package()` covers every path in the table above; no `systemctl enable` anywhere under `dist/` except inside `helper-enable` |
| same | Every unit passes `systemd-analyze verify` (when available; skipped with a message otherwise) |
| same | `mirqab.desktop` passes `desktop-file-validate` (when available) |
| `tests/test-release.sh` | `tools/release.sh --dry-run` on a fixture repository: refuses a dirty tree, a wrong branch, a version mismatch; creates no tag in dry-run; contains no `git push` |
| CI job `package` (tags and changes under `dist/`) | `makepkg` in a clean container as an unprivileged user; `namcap`; install the package; `mirqab status` runs; the helper unit is installed and `systemctl is-enabled` says disabled; remove the package and check nothing is left outside the user's own state |

## Acceptance

1. `makepkg -si` from `dist/` on a clean Arch system gives a working
   `mirqab open` after enabling the socket.
2. `namcap` reports no errors.
3. After install, nothing runs as root and no system unit is enabled.
4. `pacman -R mirqab` removes every packaged file; the user's
   `~/.config/mirqab` and `~/.local/state/mirqab` stay, as pacman
   packages do.
5. `tools/release.sh --dry-run` prints the steps and changes nothing.

## Unverified

- Whether `libpulse` can be an optional dependency. A binary linked
  against `libpulse.so.0` does not start without it. Either the Volume
  page is behind a cargo feature that the package enables and `libpulse`
  moves to `depends` (a client library with no daemon), or the
  page loads it with `dlopen`. Decide in plan 014 step 1 and make this
  list agree.
- That the `v4_16` and `v1_6` feature floors are the real minimum: build
  once in a container with those exact library versions if one can be
  had; otherwise state the tested versions (4.24, 1.10) in the README.
- `namcap`'s opinion of a package that ships a system unit it does not
  enable (expected: none).
- That `check()` can run the Rust tests in a clean chroot (they need
  `zic` from `tzdata` for plan 016's fixtures, and a private D-Bus
  daemon for the fake services; if the chroot cannot, mark those tests
  `#[ignore]` under a `packaging` cfg and say so here).
